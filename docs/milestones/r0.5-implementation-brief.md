# R0.5 Implementation Brief

Date: 2026-07-16
Status: implemented; automated QA passed; external review and human listening QA pending

## Goal

Introduce Scene Architecture:

```text
Mode -> Mood -> Scene -> Layer Mix
```

Scenes should create real ambient variation without turning Inner Atlas into a playlist app.

## Main Architecture Choice

Use option 2: retain the current audio builder pattern temporarily, with documented constraints.

Rationale:

- R0.5 needs scene expressiveness, not a broad engine rewrite.
- The existing R0.4 engine is verified and already supports continuous layers plus one-shot Resonance.
- A narrow builder contract should be introduced only after R0.5 proves which scene parameters actually need it.

Constraints:

- Scene data must stay serializable and versionable.
- Scene data must not store Web Audio node objects, timers, callbacks, or engine references.
- Layer builders must not know UI labels, prompt copy, mode names, mood names, or scene names.
- Scene behavior should enter the engine as explicit audio parameters.
- Old sessions without `sceneId` must continue to load.
- Slider zero remains true silence.

## Scene Data Should Express

Each scene may define:

- `id`
- `moodId`
- `label`
- `description`
- continuous layer `mix`
- rain density curve
- Pad voicing
- sparse event pattern
- visual metadata
- journal/session prompt

Example shape:

```ts
{
  id: "deep_water",
  moodId: "heavy",
  label: "Deep Water",
  description: "A submerged, slow, low-lit room.",
  mix: {
    drone: 0.34,
    pad: 0.42,
    rain: 0.10,
    analog: 0.18,
    air: 0.08
  },
  audio: {
    rainCurve: "low_sparse",
    padVoicing: "warm_minor_low",
    eventPattern: "deep_bowl_sparse"
  },
  visual: {
    palette: "deep-water",
    motion: "slow"
  },
  prompt: "Let one feeling sink until it becomes shape."
}
```

## Required Audio Capabilities

R0.5 should support or prepare for:

- custom rain density curves per scene;
- alternate Pad chord voicings per scene;
- sparse event patterns;
- gongs;
- Tibetan singing bowls;
- wind chimes;
- crystal plucks or hits;
- optional realistic looping rain sample investigation.

The event system should remain sparse and intentional. Do not add hidden busy schedulers or constant ornamental triggering.

## Looping Rain Sample Investigation

Switching rain to an endless looping sample is allowed as an R0.5 investigation path, not a mandatory implementation.

Before accepting sample-backed rain:

- the loop must be seamless enough for long sessions;
- playback must pause/resume cleanly;
- volume control must preserve slider zero as true silence;
- asset loading must remain local-first;
- memory and bundle cost must be acceptable;
- fallback procedural rain must remain possible if the sample path is deferred.

## Non-Goals

- No AI.
- No backend.
- No streaming or remote audio assets.
- No broad audio-engine rewrite unless GLM/Codex classification proves it is required.
- No playlist/library UI.
- No pseudoscientific frequency claims.

## Implementation Order

1. Add serializable scene definitions.
2. Add scene selection/defaulting.
3. Save `sceneId` in active and saved sessions.
4. Preserve old sessions without scene data.
5. Resolve scene to current mix and apply through the existing engine.
6. Add constrained scene audio parameters for rain curve, Pad voicing, and event pattern.
7. Add tests for scene defaulting, persistence, old-session compatibility, and mix resolution.
8. Add focused audio tests for parameter routing where practical.
9. Human listening QA for rain curves, Pad voicings, event patterns, and any sample-backed rain.

## Acceptance Criteria

- User can enter a session with mode, mood, and scene.
- Default scene is auto-selected if the user skips scene selection.
- Scene is saved in session history.
- Older sessions without scene data still work.
- Scene definitions are serializable.
- Scene definitions express mix, rain curve, Pad voicing, event pattern, visual metadata, and prompt copy.
- Current builder pattern is retained only with documented constraints.
- Audio builders do not receive UI/product labels as behavior inputs.
- Event patterns remain sparse and cleanup-safe.
- Any sample-backed rain path is local, optional, loop-safe, and silence-safe.
- Build, typecheck, tests, relevant E2E, and human listening QA pass before merge.
